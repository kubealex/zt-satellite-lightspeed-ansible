== Close the Loop: Automatically Remediate Found CVEs

Module 3 wired up the EDA side so that Satellite's webhook reaches a
running rulebook. So far, that rulebook only logs the event. In this
module you'll extend it to actually *do* something useful: whenever a
remote execution job succeeds on a host, AAP will run a custom Python
script, `vulnerability_remediation.py`, against Satellite, scoped to
that host, and install whatever RPMs are needed to fix the CVEs it
finds - closing the remediation loop end to end.

`vulnerability_remediation.py` is a script written specifically for
this lab. It logs in to `satellite.lab` and asks two of its APIs a
question each:

- *"What CVEs affect my hosts?"* - answered by Satellite's
  **Red Hat Lightspeed > Vulnerability** page, i.e. the same dashboard
  you'd click through in the Satellite Web UI. Even though that page's
  API path contains `insights_cloud`, this is served *entirely
  on-premises* by Satellite itself, from CVE/vulnerability data that
  was already synced into Satellite during lab setup
  (`setup-satellite.sh`'s `cvemap.xml` download) - it is **not** the
  hosted `console.redhat.com` cloud service, and nothing about this
  query leaves the lab network.
- *"Which package fixes each one?"* - answered by Satellite's
  documented Katello content API, which returns the exact erratum and
  RPM(s) that remediate a given CVE.

When scoped to a single host (`--host <hostname>`), the script narrows
that down further: it also pulls the host's installed package list and
compares versions, so its output is exactly the set of packages that
host needs - already in a form the remediation playbook can hand
straight to Ansible's `dnf` module.

`rhel1.lab` and `rhel2.lab` already have a handful of deliberately
vulnerable packages installed (seeded during lab setup) so you have
real CVEs to remediate.

.Step 1 - Review the pre-populated finder + remediation files
[%collapsible]
=====
To keep this module focused on *wiring things together* rather than on
copy-pasting an ~800-line script by hand, three files were already
placed on `aap1.lab` for you during lab setup, self-hosted as a git
repo at `~/vulnerability-remediation` (same pattern as the
`~/satellite-webhook` repo from Module 3, reusing its deploy key).

Click on the tab labelled `aap1.lab terminal`, then take a look:

[source,bash,role="execute"]
----
sudo -u aap1-user bash -c 'ls -la ~/vulnerability-remediation'
----

You should see three files. Here's why each one exists:

[cols="1,3"]
|===
| File | Why it's needed

| `vulnerability_remediation.py`
| The custom script explained above - queries Satellite's on-premises
  Red Hat Lightspeed Vulnerability data for CVEs, cross-references
  Satellite's Katello errata API for fixes, and (with `--host`) narrows
  that down to exactly the packages one host needs.

| `find_and_remediate.yml`
| The Ansible playbook the Job Template (Step 4) actually runs. It calls
  `vulnerability_remediation.py` scoped to the host that triggered the
  webhook, then installs whatever packages the report returns via
  `ansible.builtin.dnf`.

| `Containerfile`
| Defines the custom Execution Environment built in Step 2.
  `vulnerability_remediation.py` needs `uv` on its `$PATH` (its
  `#!/usr/bin/env -S uv run --script` shebang), which AAP's stock
  Execution Environments don't ship.
|===

Take a look at the playbook to see exactly how the scan result feeds
into the install step:

[source,bash,role="execute"]
----
sudo -u aap1-user bash -c 'cat ~/vulnerability-remediation/find_and_remediate.yml'
----

Next, we'll build the custom Execution Environment these files need.

.Step 2 - Build the custom Execution Environment
[%collapsible]
=====
`vulnerability_remediation.py` needs `uv` on its `$PATH`, which AAP's
stock Execution Environments don't ship - that's what the `Containerfile`
from Step 1 adds. Build and push it to AAP's own Hub registry, then
register it with Controller.

Still on the `aap1.lab terminal` tab, as root. Root's `podman` was
already logged into `registry.redhat.io` for you during provisioning,
so the base image in `Containerfile` can be pulled without any
credentials of your own:

[source,bash,role="execute"]
----
cd /home/aap1-user/vulnerability-remediation
podman build -t ee-vuln-finder -f Containerfile .
podman tag ee-vuln-finder:latest aap1.lab/ee-vuln-finder:latest

podman login --tls-verify=false -u admin -p "bc31c9a6-9ff0-11ec-9587-00155d1b0702" aap1.lab
podman push --tls-verify=false aap1.lab/ee-vuln-finder:latest
----

Now register it as an Execution Environment in Controller:

[source,bash,role="execute"]
----
export CTRL_API="https://localhost/api/controller/v2"
export CTRL_AUTH="admin:bc31c9a6-9ff0-11ec-9587-00155d1b0702"

EE_ID=$(curl -sk -u "$CTRL_AUTH" "$CTRL_API/execution_environments/?name=Vulnerability%20Finder%20EE" \
  | python3 -c "import sys,json; r=json.load(sys.stdin)['results']; print(r[0]['id'] if r else '')")

if [ -z "$EE_ID" ]; then
  EE_ID=$(curl -sk -u "$CTRL_AUTH" -X POST "$CTRL_API/execution_environments/" \
    -H "Content-Type: application/json" \
    -d '{"name": "Vulnerability Finder EE", "image": "aap1.lab/ee-vuln-finder:latest", "pull": "missing"}' \
    | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")
fi
echo "EE_ID=$EE_ID"
----

Now let's create the Satellite API credential the playbook will use.

.Step 3 - Create the Satellite API credential
[%collapsible]
=====
The playbook needs Satellite admin credentials, but the rulebook
shouldn't have to know them - a Controller credential injects them
automatically whenever the Job Template runs. Still as root on
`aap1.lab terminal`:

[source,bash,role="execute"]
----
export CTRL_API="https://localhost/api/controller/v2"
export CTRL_AUTH="admin:bc31c9a6-9ff0-11ec-9587-00155d1b0702"

CRED_TYPE_ID=$(curl -sk -u "$CTRL_AUTH" "$CTRL_API/credential_types/?name=Satellite%20API%20Credentials" \
  | python3 -c "import sys,json; r=json.load(sys.stdin)['results']; print(r[0]['id'] if r else '')")

if [ -z "$CRED_TYPE_ID" ]; then
  CRED_TYPE_ID=$(curl -sk -u "$CTRL_AUTH" -X POST "$CTRL_API/credential_types/" \
    -H "Content-Type: application/json" \
    -d '{
      "name": "Satellite API Credentials",
      "kind": "cloud",
      "inputs": {
        "fields": [
          {"id": "username", "type": "string", "label": "Username"},
          {"id": "password", "type": "string", "label": "Password", "secret": true}
        ],
        "required": ["username", "password"]
      },
      "injectors": {
        "extra_vars": {"satellite_username": "{{ username }}"},
        "env": {"SATELLITE_PASSWORD": "{{ password }}"}
      }
    }' | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")
fi
echo "CRED_TYPE_ID=$CRED_TYPE_ID"

CRED_ID=$(curl -sk -u "$CTRL_AUTH" "$CTRL_API/credentials/?name=Satellite%20Admin%20(API)" \
  | python3 -c "import sys,json; r=json.load(sys.stdin)['results']; print(r[0]['id'] if r else '')")

if [ -z "$CRED_ID" ]; then
  CRED_ID=$(curl -sk -u "$CTRL_AUTH" -X POST "$CTRL_API/credentials/" \
    -H "Content-Type: application/json" \
    -d "{\"name\": \"Satellite Admin (API)\", \"organization\": 1, \"credential_type\": $CRED_TYPE_ID, \"inputs\": {\"username\": \"admin\", \"password\": \"bc31c9a6-9ff0-11ec-9587-00155d1b0702\"}}" \
    | python3 -c "import sys,json; print(json.load(sys.stdin)['id'])")
fi
echo "CRED_ID=$CRED_ID"
----

.Step 4 - Create the Controller Project and Job Template
[%collapsible]
=====
This step reuses Module 3's deploy key as the SCM credential, creates a
Project pointing at the self-hosted `vulnerability-remediation` repo,
waits for it to sync, then creates the Job Template and attaches the
Satellite credential from Step 3 to it. Rather than pasting that logic
by hand, it was already written to `/root/create-controller-project.sh`
during lab setup - take a look, then run it, still as root on
`aap1.lab terminal`:

[source,bash,role="execute"]
----
cat /root/create-controller-project.sh
----

[source,bash,role="execute"]
----
/root/create-controller-project.sh
----

[NOTE]
====
`ask_variables_on_launch: true` is required - it's what allows the EDA
rulebook to pass `host_name` as an extra var when it launches this job
template in Step 5. Without it, Controller ignores any extra vars
supplied at launch time.

.Step 5 - Wire the rulebook to launch the Job Template
[%collapsible]
=====

launches the Job Template whenever a job succeeds. This also writes

the EDA Project, and recreates the Activation with both credentials
(Basic Auth + the new AAP Controller credential) attached. All of that
was already written to `/root/wire-rulebook.sh` during lab setup - take
a look, then run it, still on `aap1.lab terminal` as root:
