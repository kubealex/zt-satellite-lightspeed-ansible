== Close the Loop: Automatically Remediate Found CVEs

Module 3 wired up the EDA side so that Satellite's webhook reaches a
running rulebook. So far, that rulebook only logs the event. This module
extends it to *do* something useful. Whenever a remote execution job
succeeds on a host, AAP runs a custom Python script,
`vulnerability_remediation.py`, against Satellite. The script finds
every host affected by a remediable CVE and the exact RPMs each one
needs. AAP then installs those RPMs across *all* the affected hosts,
closing the remediation loop end to end. A webhook from a single host is
only the *trigger*. The remediation itself is fleet-wide, not scoped to
whichever host happened to fire the event.

.How the remediation flow works
image::remediation-sequence-diagram.png[Sequence diagram showing the rulebook launching the Job Template, vulnerability_remediation.py querying Satellite's Lightspeed Vulnerability and Katello errata APIs, then Ansible installing the fixed packages on every affected host]

`vulnerability_remediation.py` is a script written specifically for
this lab. It logs in to `satellite.lab` and asks two of its APIs a
question each:

- *"What CVEs affect my hosts?"* is answered by Satellite's
  **Red Hat Lightspeed > Vulnerability** page, the same dashboard shown
  in the Satellite Web UI. That page's API path contains
  `insights_cloud`, but it is served *entirely on-premises* by Satellite
  itself, from CVE data that was already synced into Satellite during
  lab setup (`setup-satellite.sh`'s `cvemap.xml` download). It is
  **not** the hosted `console.redhat.com` cloud service. Nothing about
  this query leaves the lab network.
- *"Which package fixes each one?"* is answered by Satellite's
  documented Katello content API, which returns the exact erratum and
  RPM(s) that remediate a given CVE.

[NOTE]
====
By default the script reports only CVEs rated Critical or Important
(`DEFAULT_SEVERITIES = ["Critical", "Important"]`), and the remediation
playbook runs it with that default. This lab's automated remediation
policy is therefore scoped to Critical and Important CVEs. CVEs rated
Moderate, Low, or None are surfaced in the Module 2 dashboard but are
not auto-remediated. Widening the policy means passing additional
`--severity` values to the script in `find_and_remediate.yml`.
====

When scoped to a single host (`--host <hostname>`), the script narrows
that down further. It also pulls that host's installed package list and
compares versions. Its output is then exactly the set of packages that
one host needs, in a form the remediation playbook can hand straight to
Ansible's `dnf` module. The playbook uses this per-host mode for each
affected host in turn (see Step 1).

`rhel1.lab` and `rhel2.lab` already have a handful of deliberately
vulnerable packages installed, seeded during lab setup. These provide
real CVEs to remediate.

[NOTE]
====
Building and registering a custom Execution Environment is a routine
AAP administration task, and this lab is not about teaching AAP
configuration itself. That work was already done during lab setup. This
module focuses on Satellite's CVE data and Ansible's remediation logic

Next, create the Satellite API credential the playbook will use.

.Step 2 - Create the Satellite API credential
[%collapsible]
=====
The playbook needs Satellite admin credentials, but the rulebook should
not have to know them. A Controller credential injects them
automatically whenever the Job Template runs.

Two Controller objects are involved. A *credential type* defines the
shape of the credential: which fields it holds, and how those fields
reach a running job. A *credential* is one filled-in instance of that
type. Satellite is not one of Controller's built-in credential types, so
this lab defines its own.

Like the scripts in the next two steps, the playbook that creates them
was already written to `/root/create-satellite-credential.yml` during
lab setup:

[source,yaml]
----
- name: Create the Satellite API credential in Controller
  hosts: localhost
  connection: local
  gather_facts: false
  tasks:
    - name: Define the Satellite API credential type
      ansible.controller.credential_type:
        name: Satellite API Credentials
        kind: cloud
        inputs:
          fields:
            - id: username
              type: string
              label: Username
            - id: password
              type: string
              label: Password
              secret: true
          required:
            - username
            - password
        injectors:
          extra_vars:
            satellite_username: !unsafe '{{ username }}'
          env:
            SATELLITE_PASSWORD: !unsafe '{{ password }}'
        state: present

    - name: Create the Satellite admin credential
      ansible.controller.credential:
        name: Satellite Admin (API)
        organization: Default
        credential_type: Satellite API Credentials
        inputs:
          username: admin
          password: bc31c9a6-9ff0-11ec-9587-00155d1b0702
        state: present
----

The `injectors` block is the part that matters. It is what makes the
credential *usable without being known*: at launch time Controller
hands the username to the playbook as the `satellite_username` extra
var, and the password as the `SATELLITE_PASSWORD` environment variable.
Those are exactly the two things `find_and_remediate.yml` consumes when
it calls `vulnerability_remediation.py --username {{ satellite_username }}`.
The password is never written into the playbook, the rulebook, or the
repo.

[NOTE]
====
`!unsafe` on those two values is required, not decoration. `{{ username }}`
and `{{ password }}` are *Controller's* templates, filled in by Controller
when it launches a job. Without `!unsafe`, Ansible would try to resolve
them while creating the credential type and fail on an undefined variable.
====

Still as root on the `aap1.lab terminal` tab, run it:

[source,bash,role="execute"]
----
ansible-playbook /root/create-satellite-credential.yml
----

Re-running it is safe. Both tasks use `state: present`, so a second run
reports `ok` rather than creating a duplicate.

Then create the Controller Project and Job Template.

.Step 3 - Create the Controller Project and Job Template
[%collapsible]
=====
Rather than pasting that logic by hand, it was already written to
`/root/create-controller-project.yml` during lab setup. Running it does
the following, in order:

* Reuses Module 3's deploy key as the SCM credential, so Controller
  can pull the self-hosted `vulnerability-remediation` repo.
* Creates a Controller Project pointing at that repo, then waits for
  it to finish syncing.
* Creates the Job Template that runs `find_and_remediate.yml`, using
  the custom Execution Environment already registered during lab
  setup.
* Attaches the Satellite credential from Step 2 to the Job Template,
  so it can authenticate without the rulebook ever needing to know the
  password.
* Attaches a Machine credential (the lab's SSH key, connecting as
  `root`) to the Job Template. The playbook's second play installs the
  fixed RPMs *on the affected host* over SSH, so without a Machine
  credential every host would fail with `Permission denied (publickey)`.

Still as root on the `aap1.lab terminal` tab, run it:

[source,bash,role="execute"]
----
ansible-playbook /root/create-controller-project.yml
----

[NOTE]
====
`ask_variables_on_launch: true` is required. It allows the EDA rulebook
to pass `host_name` (the host that fired the webhook) as an extra var
when it launches this job template in Step 4. Without it, Controller
ignores any extra vars supplied at launch time. The playbook keeps
`host_name` only for the audit trail. It remediates every affected host
regardless of which one triggered the run.
====

Finally, wire the rulebook to actually launch that Job Template.

.Step 4 - Wire the rulebook to launch the Job Template
[%collapsible]
=====
All of that was already written to `/root/wire-rulebook.yml` during lab
setup. Running it does the following, in order:

* Creates an AAP Controller credential in EDA, so the rulebook can
  authenticate to Controller's API when it launches the Job Template.
* Extends the rulebook so that, whenever a remote execution job
  succeeds, it both logs the event *and* launches the Job Template. The
  triggering host is passed through as an extra var for the audit trail,
  and the playbook still remediates every affected host. It then pushes
  the updated rulebook to the self-hosted repo. This is done by
  adding a second *action* to the existing success rule rather than a
  second *rule*. The ansible-rulebook engine fires only one rule per
  event, since the first matching rule consumes it. A separate
  remediation rule sitting behind the catch-all log rule would never
  fire.
* Resyncs the EDA Project so it picks up that change.
* Recreates the Activation with both credentials attached (the Basic
  Auth credential from Module 3 and the new AAP Controller
  credential), and the updated rulebook hash.

Still on the `aap1.lab terminal` tab as root, run it:

[source,bash,role="execute"]
----
ansible-playbook /root/wire-rulebook.yml
----
