== Close the Loop: Automatically Remediate Found CVEs

Module 2 wired up the EDA side so that Satellite's webhook reaches a
running rulebook. So far, that rulebook only logs the event. In this
module you'll extend it to actually *do* something useful: whenever a
remote execution job succeeds on a host, AAP will run a custom Python
script, `vulnerability_remediation.py`, against Satellite, scoped to
that host, and install whatever RPMs are needed to fix the CVEs it
finds - closing the remediation loop end to end.

`vulnerability_remediation.py` is a script written specifically for
this lab. It logs in to `satellite.lab` and asks two of its APIs a
question each:

- *"What CVEs affect my hosts?"* - answered by Satellite's
  **Red Hat Lightspeed > Vulnerability** page, i.e. the same dashboard
  you'd click through in the Satellite Web UI. Even though that page's
  API path contains `insights_cloud`, this is served *entirely
  on-premises* by Satellite itself, from CVE/vulnerability data that
  was already synced into Satellite during lab setup
  (`setup-satellite.sh`'s `cvemap.xml` download) - it is **not** the
  hosted `console.redhat.com` cloud service, and nothing about this
  query leaves the lab network.
- *"Which package fixes each one?"* - answered by Satellite's
  documented Katello content API, which returns the exact erratum and
  RPM(s) that remediate a given CVE.

When scoped to a single host (`--host <hostname>`), the script narrows
that down further: it also pulls the host's installed package list and
compares versions, so its output is exactly the set of packages that
host needs - already in a form the remediation playbook can hand
straight to Ansible's `dnf` module.

`rhel1.lab` and `rhel2.lab` already have a handful of deliberately
vulnerable packages installed (seeded during lab setup) so you have
real CVEs to remediate.

.Step 2 - Build the custom Execution Environment
[%collapsible]
=====
`vulnerability_remediation.py` needs `uv` on its `$PATH`, which AAP's
stock Execution Environments don't ship - that's what the `Containerfile`
from Step 1 adds. Build and push it to AAP's own Hub registry, then
register it with Controller.

Still on the `aap1.lab terminal` tab, as root:

[source,bash,role="execute"]
----
# The base image comes from registry.redhat.io, which needs its own
# pull credentials (separate from AAP's own admin login).
podman login registry.redhat.io --username "<your-redhat-registry-username>" --password "$REGISTRY_PULL_TOKEN"

cd /home/aap1-user/vulnerability-remediation
podman build -t ee-vuln-finder -f Containerfile .
podman tag ee-vuln-finder:latest aap1.lab/ee-vuln-finder:latest

podman login --tls-verify=false -u admin -p "bc31c9a6-9ff0-11ec-9587-00155d1b0702" aap1.lab
podman push --tls-verify=false aap1.lab/ee-vuln-finder:latest
----

[TIP]
====
If `registry.redhat.io` pull credentials aren't set up the way this
lab's `$REGISTRY_PULL_TOKEN` expects, and `podman login` fails, check
whether the base image is already cached locally first
(`podman images | grep ee-supported-rhel9`) - some lab images pre-pull
it, in which case you can skip straight to the `podman build` line.
====

curl -sk -u "$CTRL_AUTH" -X POST "$CTRL_API/job_templates/$JT_ID/credentials/" \

[source,bash,role="execute"]

If the versions changed from what you saw at the start of this step,
congratulations - the entire loop is closed: Satellite fired a webhook,
EDA validated and routed it, AAP launched a job that found the
applicable CVEs via Red Hat Lightspeed, and Ansible installed the exact
packages needed to fix them, with zero manual intervention.

[TIP]
====
If the job status shows `failed`, the `stdout` output in the previous
command is the first place to look - most failures at this point are
either the Satellite API credential/URL, the Execution Environment not
having `uv` (double-check Step 2's build succeeded), or
`vulnerability_remediation.py` not being present in the repo (Step 1's
note about placing it there yourself).
====
