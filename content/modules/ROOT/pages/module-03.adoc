== Configure the Satellite Webhook

In the previous module you logged into both the Satellite and AAP Web
UIs. Behind the scenes, `aap1.lab` was already configured during
provisioning with an Event-Driven Ansible (EDA) pipeline: a self-hosted
rulebook repository, an EDA Project, a Basic Auth credential, an Event
Stream, and a running Rulebook Activation.

[NOTE]
====
EDA has *already* been minimally configured for you to *receive*
webhooks, so you won't be building an EDA pipeline from scratch in this
module. That's a deliberate choice, since this lab is meant to give you
an end-to-end overview of how Satellite and AAP's EDA fit together to
close the remediation loop, not to teach you every detail of
configuring EDA itself. The one piece EDA genuinely can't do for you,
because it lives entirely on Satellite's side, is telling Satellite to
call that Event Stream. That's the only thing you'll configure in this
module.
====

What's still missing is the other end of the pipe: *Satellite* doesn't
know to call that Event Stream yet. In this module, you'll configure
Satellite's webhook so that every time a remote execution job succeeds
on a host, Satellite calls AAP's EDA Event Stream - closing the loop.

image::instances-diagram.png[Lab environment instances, as defined in config/instances.yaml]

.How the webhook flow works
image::webhook-sequence-diagram.png[Sequence diagram of Satellite calling AAP's EDA Event Stream, which delivers the event to the running rulebook Activation]

. *Remote execution job succeeds* - Satellite finishes running a
  command on a host (e.g. `rhel1.lab`) and the job reports success.
. *Satellite -> AAP Gateway* - Satellite's Webhook fires an HTTPS POST
  to the Event Stream's URL, authenticated with the Basic Auth
  username/password you configure in Step 3. This request lands on
  AAP's Gateway, the single front door for every AAP component on
  `aap1.lab`.
. *AAP Gateway -> EDA Event Stream* - the Gateway routes the request
  internally to the matching `external_event_stream/<uuid>/post/`
  endpoint inside EDA.
. *EDA validates the credentials* - the Event Stream checks the
  request's Basic Auth against the credential it was created with. A
  mismatch (or a stale/incorrect URL) is rejected here, before the
  event ever reaches a rulebook.
. *EDA Event Stream -> Activation* - once validated, EDA delivers the
  event to the running Rulebook Activation whose source mapping links
  to this Event Stream.
. *Rule fires -> action runs* - the Activation's rulebook evaluates its
  condition (currently `condition: true`, so it always matches) and
  runs its action - right now just logging the event, which is what
  Step 4 checks for in the Activation's logs.

======
First, let's look up the Event Stream URL and credentials that `aap1.lab` already generated.

.Step 1 - Look up the Event Stream URL and credentials
[%collapsible]
=====
`aap1.lab`'s setup already generated a Basic Auth username/password and
an Event Stream URL, and saved them to a file in `aap1-user`'s home
directory.

Click on the tab labelled `aap1.lab terminal` and log in, then run:

[source,bash,role="execute"]
----
sudo -u aap1-user bash -c 'cat ~/.eda_webhook_basic_auth.json'
----

You should see JSON similar to this (your actual values will differ):

[source,js]
----
{
  "username": "satellite-webhook",
  "password": "<a long generated password>",
  "event_stream_url": "https://aap1.lab/eda-event-streams/api/eda/v1/external_event_stream/<uuid>/post/"
}
----

You don't need to copy any of these values by hand - Step 3 fetches
them itself, live, via SSH.

[NOTE]
====
The `ansible.eda.webhook` block inside the rulebook
(`satellite-webhook.yml`) is just a placeholder name. EDA swaps it out at
runtime for its own delivery mechanism once the rulebook's source name
is linked to the Event Stream - you don't need to worry about it.
====

Next, we'll create a custom JSON webhook template, since Satellite's built-in ones don't work for this event type.

.Step 2 - Create the custom JSON webhook template
[%collapsible]
=====
Satellite's built-in webhook templates don't work for this event type:
the default "Webhook Template - Payload Default" template throws
`undefined method '#id'`, and the other built-in "Remote Execution Host
Job" template only emits human-readable comments, not JSON. You need a
custom template that renders real JSON.

Click on the tab labelled `satellite.lab terminal`, log in as `root`,
and run:

[source,bash,role="execute"]
----
cat > /tmp/satellite-remote-execution-host-job-json.erb <<'EOF'
<%#
name: Satellite Remote Execution Host Job JSON
description: JSON payload for actions.remote_execution.run_host_job_succeeded.event.foreman
snippet: false
model: WebhookTemplate
-%>
<%=
payload({
  host_name: @object.host_name,
  host_id: @object.host_id,
  job_invocation_id: @object.job_invocation_id,
  task_label: @object.task.label,
  task_state: @object.task.state,
  task_result: @object.task.result,
  task_started_at: @object.task.started_at,
  task_ended_at: @object.task.ended_at
})
-%>
EOF

TEMPLATE_CONTENT=$(cat /tmp/satellite-remote-execution-host-job-json.erb)
hammer webhook-template create \
  --name "Satellite Remote Execution Host Job JSON" \
  --template "$TEMPLATE_CONTENT" \
  --snippet false
----

Now let's create the webhook itself, pointing it at the Event Stream.

.Step 3 - Create the webhook
[%collapsible]
=====
Still on the `satellite.lab terminal` tab, create the webhook itself.
Rather than copying `EVENT_STREAM_URL`/`WEBHOOK_USER`/`WEBHOOK_PASS` from
Step 1 by hand, this fetches them itself, live, over SSH to `aap1.lab` -
that also sidesteps the Event Stream URL/UUID going stale if the Basic
Auth credential is touched again later (a copied value would fail with
`{"detail":"bad uuid specified"}` in that case; a freshly-fetched one
never can):

[source,bash,role="execute"]
----
EDA_SECRET=$(ssh -o StrictHostKeyChecking=no aap1-user@aap1.lab "cat ~/.eda_webhook_basic_auth.json")
WEBHOOK_USER=$(echo "$EDA_SECRET" | python3 -c "import sys,json;print(json.load(sys.stdin)['username'])")
WEBHOOK_PASS=$(echo "$EDA_SECRET" | python3 -c "import sys,json;print(json.load(sys.stdin)['password'])")

EVENT_STREAM_URL=$(ssh -o StrictHostKeyChecking=no aap1-user@aap1.lab \
  "curl -sk -u 'admin:bc31c9a6-9ff0-11ec-9587-00155d1b0702' 'https://localhost/api/eda/v1/event-streams/?name=Satellite%20Remote%20Execution%20Webhook'" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['results'][0]['url'])")

hammer webhook create \
  --name "AAP Event Driven Ansible Webhook" \
  --target-url "$EVENT_STREAM_URL" \
  --http-method POST \
  --http-content-type "application/json" \
  --event "actions.remote_execution.run_host_job_succeeded" \
  --webhook-template "Satellite Remote Execution Host Job JSON" \
  --user "$WEBHOOK_USER" \
  --password "$WEBHOOK_PASS" \
  --verify-ssl false \
  --enabled true
----

[IMPORTANT]
====
The `--event` value has *no* `.event.foreman` suffix on input, even
though `hammer webhook info` will display it *with* that suffix
afterward. Use `actions.remote_execution.run_host_job_succeeded` exactly
as shown above.

Finally, let's verify the whole pipeline fires end-to-end.

.Step 4 - Verify end-to-end
[%collapsible]
=====
First, trigger a remote execution job against one of the RHEL hosts.
Still on the `satellite.lab terminal` tab, run:

[source,bash,role="execute"]
----
hammer job-invocation create \
  --job-template "Run Command - Ansible Default" \
  --search-query "name = rhel1.lab" \
  --inputs "command=echo webhook-test"
----

Now switch back to the `aap1.lab terminal` tab and check that the Event
Stream received it and the rulebook's rule fired:

[source,bash,role="execute"]
----
export EDA_API="https://localhost/api/eda/v1"
export EDA_AUTH="admin:bc31c9a6-9ff0-11ec-9587-00155d1b0702"

curl -sk -u "$EDA_AUTH" "$EDA_API/event-streams/?name=Satellite%20Remote%20Execution%20Webhook" \
  | python3 -c "import sys,json; d=json.load(sys.stdin)['results'][0]; print('events_received:', d['events_received']); print('last_event_received_at:', d['last_event_received_at'])"
----

`events_received` should have gone up by one, and `last_event_received_at`
should show the current time. If you want to see the actual payload
Satellite sent, check the Rulebook Activation's logs:

[source,bash,role="execute"]
----
ACTIVATION_ID=$(curl -sk -u "$EDA_AUTH" "$EDA_API/activations/?name=Satellite%20Webhook%20Activation" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['results'][0]['id'])")
INSTANCE_ID=$(curl -sk -u "$EDA_AUTH" "$EDA_API/activations/$ACTIVATION_ID/" \
  | python3 -c "import sys,json; print(json.load(sys.stdin)['instances'][0])")
curl -sk -u "$EDA_AUTH" "$EDA_API/activation-instances/$INSTANCE_ID/logs/" | tail -c 2000
----

You should see a line like:

[source,js]
----
Received Satellite webhook: {'payload': {'host_name': 'rhel1.lab', 'task_result': 'success', ...}, 'meta': {...}}
----

If you see that line with the current timestamp, congratulations - the
Satellite-to-AAP EDA webhook pipeline is fully wired up end to end.

[TIP]
====
If `events_received` didn't increase, check
`/var/log/foreman/production.log` on `satellite.lab` around the time you
ran the job for lines containing `EventSubscriber` or `webhook`. A Ruby
exception there usually means the webhook *template* is misconfigured
for this event type - double-check Step 2.
====
